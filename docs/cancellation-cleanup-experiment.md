# Cancellation cleanup experiment

The generated cancellation cleanup overlay is experimental and is excluded from normal native snapshots. Set `WINE11_EXPERIMENT_CANCEL_CLEANUP=1` both when preparing the native snapshot and when running the native link probe to opt in for local diagnostics. Review assembly rejects snapshots containing the generated overlay. Host tests in `tools/test.sh` exercise the experiment regardless of that opt-in.

The overlay tracks pending cleanup and errors only within the running process. It does not durably record cancellation or failures across a crash or restart. Known-root cleanup failures can be retried from Downloads; failures without an available root remain visible and block exit and account changes, with no in-session retry. The generic multi-volume API lacks the authoritative mount and device identity needed to safely identify a reconnected volume. This is not release-ready and has not been validated on a console.

`prepare_steam_cancel_failure_experiment.py` is a separate host-test-only experiment, not used by normal snapshot or title assembly. Its cleanup retry is not approved: the underlying path-based remover can follow an intermediate symlink, and an install record may appear before deletion. The normal candidate therefore retains the previous quiescence behavior and still does not report canceled-download removal errors. Do not deploy the experiment.

## Durable design to investigate

Use a separate per-game cleanup journal under the already admitted private state directory, owned by the existing state lease. A record should contain a version, Steam app ID, volume identity and generation, operation ID, and cleanup phase; it must not authorize an arbitrary path. Keep the game unavailable for reinstall or account transition from acceptance of cancellation until the cleanup journal is durably cleared. The game root must be reconstructed from the app ID and the currently anchored, validated games directory, then passed through the existing guarded runner and install lease.

The persistence owner should be a serialized worker. It receives immutable requests and completes them asynchronously; neither it nor its callers may wait for the process-wide effective-UID guard while holding the install-service mutex. The current guarded install runner holds the UID guard while progress callbacks acquire that mutex, so writing synchronously from `Cancel` or `Publish` can deadlock. Service state changes and persistence completions need operation IDs and generation checks so stale completions cannot authorize a different install. A successful install racing cancellation needs a defined winner before any cleanup is authorized.

The active download holds that same UID guard for its entire transfer. Cancellation therefore cannot wait for journal preparation before signaling the runner: that can postpone cancellation until the download finishes. The opt-in quiesce mode signals the runner, retains canceled jobs, and schedules journal preparation on the service worker after the runner returns and outside the service mutex. It does not invoke removal. A host test exercises the UID-lock ordering and the in-memory rule that a successful install wins the cancellation race. That winner is not yet durably recorded, and removal and complete restart recovery remain unimplemented.

`NativeSession` owns the validated state directory and its lease and outlives its runtime. In the opt-in build it passes both by reference to a recovery capability, which checks the directory and lease and reads the journal before the generated service scans its registry or starts its worker. The callback currently always refuses startup: a valid lease or readable journal alone is not evidence that recovery occurred. Refusal is visible and blocks downloads, exit and account changes; the host tests check the lease and gate. Other service constructors can still start without the gate, so this is a tested prerequisite, not recovery. Normal non-overlay builds are unchanged.

An experimental single-operation journal uses durable storage and validates state and games leases. It first records a prepared operation and target device, inode and nonce, then can create a target marker and promote the record to intent after durable marker verification. A failed marker write remains prepared; a complete marker after an indeterminate sync may be revalidated before promotion. Completion is disabled and the runtime gate stays closed. Calls must not hold the install-service mutex because they can wait for the process-wide UID lock.

A pre-scan reconciliation experiment reads a valid pending journal, checks the target identity and marker, and refuses a present or uninspectable completed-install record. Its planner removes only an exact queued or paused entry on the internal volume, preserving other lines; unexpected target entries, duplicates and truncated input block it. An explicitly opted-in experimental startup can write the games registry for a valid pending intent even though startup remains blocked. The proposed registry is written through `Storage::WriteDurable` and verified by a durable reread, while the journal remains pending and startup stays blocked. Host tests cover a present install record and a directory-sync failure after rename followed by a retry. A failed write is indeterminate, not evidence that the old registry remains. This path relies on the exclusive install lease and execution before the worker starts; its console behavior and the interaction with a previously completed but non-durable install record remain unproven.

An experimental target-evidence helper requires an existing Playden marker, writes an exclusive nonce marker and checks target identity. Its nonce is supplied by the caller; uniqueness and unpredictability are not established. This is not deletion authorization or cryptographic authentication and assumes cooperating writers. The journal API records a prepared operation before marker creation, but the low-level helper remains callable independently; old or externally created orphan markers still need reconciliation. No runtime calls the marker creator.

Before deleting, atomically publish and sync the cleanup intent, including its parent directory. `Storage::WriteDurable` already implements checked temporary-file write, file sync, rename and directory sync, but it can return an error after rename has made the new record visible. Such a result is indeterminate: preserve the files, and authorize no deletion until the record is validated and both its file and parent directory have been successfully synced. `Storage::ReadDurable` performs those barriers; visibility from an ordinary read alone is insufficient. A successfully durable rewrite is another possible reconciliation. Admission, locked directory identity and ownership must be revalidated at every attempt. Do not overwrite the existing game registry with an unacknowledged update or interpret its absence as proof of cleanup.

On startup, read and validate outstanding journals before allowing a new install of those IDs; show recovery status rather than starting an unrelated download. A missing, unavailable, changed or unidentifiable volume must remain blocked and visible. Do not reuse a remembered mount path as proof that the same external device is attached. On deletion failure, retain the journal and show a retry action. A completed-cleanup tombstone must remain authoritative until the queue registry's removal of the canceled job is durably acknowledged; the existing `SaveRegistry` ignores write, rename and sync errors, so its return is not such an acknowledgment. Otherwise a crash can resurrect the old queued download after cleanup. Repeating cleanup after a crash requires verified idempotence of the real removal implementation, including the case where the directory is already gone; this remains unproven. The current generic volume API does not preserve mount identity and needs an authoritative identity provider before it can support this recovery safely.

The current `RemoveManagedInstall` is not suitable for this recovery unchanged. A partial download can be admitted by its `.playden-download` directory, which the removal walk may delete before it removes the game folder; an interruption can leave a folder without any marker and a subsequent call refuses it. Its `Exists` helper also treats every `stat` failure as absence, including errors other than `ENOENT`. Recovery must distinguish verified absence from an access error and use the durable operation identity and guarded directory to handle an interrupted, markerless partial cleanup without authorizing unrelated data. Both behaviors require targeted fault tests before deployment.

The opt-in snapshot applies a narrow root-check experiment: it treats only `lstat`/`ENOENT` as absent, refuses inaccessible roots, and refuses roots that are symlinks or non-directories. It still refuses markerless folders and therefore does not solve interrupted cleanup. The host test injects `EACCES` and checks the missing, markerless and symlink cases; this does not establish console filesystem semantics or cover races between the check and subsequent path operations.

The same opt-in generated downloader checks stream errors, syncs each manifest-listed regular file and its descriptor-opened parent directories, then syncs the file list, renamed install record and root directory before returning success. It reopens and compares path-component identities and fails closed on symlinks in synced paths and on cross-device paths, missing files, size mismatch and sync errors. Host tests exercise nested files and injected failures; the download journal is retained when finalization fails. The pass does not rehash resumed content, rule out concurrent namespace replacement or inode reuse, or establish PS5 runtime filesystem behavior. Rename may also have succeeded when sync fails, leaving a visible install record despite a failure result; that is an ambiguous winner, not permission to delete. The service's success-winner decision is not durably persisted.

The opt-in guarded runner also creates a UUID per install attempt and scopes it to that synchronous attempt; the generated downloader writes it in the install record. Host tests exercise missing context, distinct IDs, nested scopes and thread isolation. This UUID is not yet independently durably recorded before the attempt or compared with a winner journal, so it does not authenticate recovery.

An isolated host probe verified descriptor-relative open and identity checks, including refusal of a substituted directory and a symlink. The same probe compiled to a PS5 object, but this proves only SDK declarations. The SDK lists `openat`, `fstatat`, `unlinkat`, and directory-reading syscall numbers; the existing console shim wraps `openat` and `mkdirat`, while `fstatat` and `unlinkat` have no corresponding shim in that file. The project's PS5 `ManagedDirectory` selects an absolute-path backend. Link availability, syscall behavior, directory iteration, and identity behavior on the console have not been established; no console probe was run.

Two read-only SDK link probes were also built without execution. The direct `fstatat`/`openat` probe linked, but disassembly showed local stubs that issue raw `syscall`; its `fdopendir` and `readdir` are dynamic imports. A second probe linked with the existing `--wrap=openat` gateway and uses `fstat` on the opened descriptor. It leaves `fdopendir`, `readdir` and `sceKernelDlsym` as dynamic imports. The wrapped approach may capture an opened inode, but neither probe validates name-to-inode stability after opening or safely deletes entries. Neither proves that the title can resolve these imports or use these operations on the console.

An isolated host characterization shows a further deletion boundary: no-follow opens can reject an intermediate symlink, but `fstatat` followed by `unlinkat` cannot require that the final name still identifies the inspected inode. A writer that ignores the cooperative lease can replace that name in between, and `unlinkat` removes the replacement. Automatic deletion must remain disabled until a stronger, qualified exclusion/ownership mechanism or an explicitly narrower safety contract is established. The host test uses only a temporary fixture and does not establish PS5 syscall behavior.

Host tests should inject failures before and after temporary-file creation, writes, file sync, rename, directory sync, removal, and journal clearing; include a rename that succeeds followed by a failed directory sync. Exercise cancellation during progress callbacks, concurrent install completion, duplicate requests, shutdown, and cleanup retry without holding the service mutex across UID waits. Restart a worker at each phase using isolated temporary directories, check that partial data survives every uncommitted or failed decision, and verify no new install can race recovery. Test absent and substituted volume identities and removal idempotence. These are a proposed test plan, not evidence of console filesystem durability or completed implementation.
